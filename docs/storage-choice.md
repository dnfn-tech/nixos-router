# 配置存储选型：配置文件 vs 数据库

状态：采纳建议（待实现前确认）  
背景：产品目标靠拢家用路由器网页体验——局域网网页改配置即生效；本机状态为真源；远程 flake 部署只更新程序，不覆盖可变状态。

## 1. 要存的三类数据

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 意图配置 | WAN/LAN、DHCP 池、DNS、防火墙放行、SSH 策略 | 体量小、结构稳定、需要备份/导入导出、改完要整体校验再 apply |
| 运行/会话 | 登录 session、正在 apply 的任务、短暂锁 | 高频读写、可丢（重启失效可接受） |
| 审计与历史 | 谁在何时改了什么、配置版本、失败原因 | 追加为主、要查询/分页、可随时间变大 |

选型应分开看，不必三类共用一种介质。

## 2. 配置文件（JSON / TOML / YAML）

**优点**

- 与声明式心智接近：一份文档即当前意图，备份就是拷文件。
- 运维友好：`jq`/`cat` 可查，出问题易定位。
- 原子替换简单：写临时文件 → `fsync` → `rename`。
- 导入导出、迁移到另一台路由器成本低。
- 可选「导出进 git」不别扭；和以后生成 nix 片段也顺。
- 家用/开源路由先例多：OpenWrt UCI、pfSense/OPNsense 的 XML 配置，核心都是文件型意图配置。

**缺点**

- 并发写要自己做锁；多进程同时改容易踩脚（单管理页 + 单 agent 可接受）。
- 配置历史、审计查询弱：要么整文件拷贝当版本，要么另存。
- 局部字段更新仍倾向读改写整文件（配置小则无妨）。
- Session、任务队列用纯文件别扭。

**适合**：意图配置的真源。

## 3. 数据库（优先 SQLite）

**优点**

- 事务：校验通过再提交；apply 失败可保留「待应用」与「已应用」两版。
- 审计、版本、按时间/用户查询自然。
- Session、后台 job、租约缓存等表结构清晰。
- 单文件 SQLite 仍适合嵌在路由器，备份可拷 `state.db`。

**缺点**

- 意图配置可读性差，排障要工具或导出。
- 要做 schema migration；早期字段动荡时成本高于 JSON。
- 「打开文件就能懂当前网络怎么配」的体验变弱。
- 对首期体量（数 KB 配置）偏重，除非同时强依赖审计/任务表。

**适合**：审计、会话、任务、可选的配置版本索引；不必也不建议作为人类可读意图的唯一载体。

## 4. 对照（家用路由场景）

| 维度 | 仅配置文件 | 仅 SQLite | 文件存意图 + SQLite 辅表（推荐） |
| --- | --- | --- | --- |
| 改完即用 | 好 | 好 | 好 |
| 备份/恢复 | 最好 | 好（拷 DB） | 最好（拷 `config.json`，可选拷 DB） |
| 远程部署不丢配置 | 状态目录排除即可 | 同左 | 同左 |
| 审计与回滚 | 弱（需自建） | 强 | 强 |
| 排障可读性 | 强 | 弱 | 强 |
| 实现复杂度 | 低 | 中 | 中低 |
| 与 Nix 模块边界 | 清晰 | 清晰 | 清晰 |

## 5. 结论与约定

**推荐：混合存储。**

1. **意图配置真源**：`/var/lib/nixos-router/config.json`（或 `config.toml`）  
   - 单一文档、JSON Schema 校验、原子写。  
   - Web/API 读写的「当前配置」均来自该文件（经 agent）。  
   - 开机 activation / 服务启动：读文件 → apply 到网络/dnsmasq/nft 等。

2. **SQLite**：`/var/lib/nixos-router/state.db`  
   - 表建议：`sessions`、`audit_log`、`config_revisions`（可选：每次保存把完整 JSON 快照或 diff 存一行）、`jobs`（apply 状态）。  
   - 不把「当前意图」只放在 DB 而不落文件，避免排障只能查库。

3. **Nix 闭包**  
   - 只提供程序、单元、权限、默认空配置模板；**不**把用户网页改动编进 store。  
   - 状态目录列入持久化（安装/重建系统时保留 `/var/lib/nixos-router`）。

4. **不采用**  
   - 每次保存生成 nix 再远程 `rebuild` 当主路径（与家用体验冲突，且易被管理机闭包覆盖）。  
   - 纯 DB 无导出文件（备份与可见性差）。

## 6. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 写配置过程中断电 | 原子 rename；可选写前拷贝 `config.json.bak` |
| apply 成功但文件未写入（或相反） | 先写文件并记录 revision，再 apply；失败则标记 `jobs` 并允许重试/回滚到上一 revision |
| 文件被手改坏 | 启动与保存均做 schema 校验；不通过则拒绝 apply 并保留上份 bak |
| 只备份了 JSON 丢了审计 | 文档说明完整备份含 `state.db`；审计非恢复网络所必需 |
